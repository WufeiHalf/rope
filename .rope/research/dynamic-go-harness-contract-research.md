## Concrete mechanics and limits

- `pipeline` is streaming per item with no stage barrier; `parallel` is an explicit barrier (`tool-description.ts:75-85`).
- Current documented runtime caps are real source constants/parameters, not merely prose: concurrency defaults to `workflowConcurrency()` (`runtime.ts:593`), while the user-facing contract states `min(16, available CPUs - 2)`, lifetime agent cap 1000, and per-call item cap 4096 (`tool-description.ts:115-117`). Runtime-internal options expose `concurrency`, `agentCap`, `itemCap`, and `nestedCap`; these are not automatically public per-script knobs. The verified default is `max(1,min(16,cpus-2))` (`runtime.ts:48-50`); the parent independently ran `node:os.cpus().length` (16), deriving a current default ceiling of 14. This is a maximum simultaneous agent-call count, not a recommended workload size.
- Nested workflows share concurrency, agent counter, abort signal and budget; nesting is one level only (`tool-description.ts:88-89`).
- `resumeFromRunId` replays the longest unchanged prefix, not arbitrary completed calls; the first changed/new call and all after it run live. A journaled failure ends the reusable prefix (`tool-description.ts:199-201`). This is safe for deterministic orchestration but does **not** make side effects idempotent: merge/gate operations need durable commit checks and idempotent commands, and edits before the changed call invalidate later cache reuse.
- Inline scripts are persisted automatically; repeatable scripts belong in `.pi/workflows`, `.agents/workflows`, or an agent-dir `workflows`; named workflows resolve through the same registry (`tool-description.ts:46-48,88-89`; `src/workflow/saved.ts:166-205`). Scripts cannot load files or Node APIs, and `eval`/`Function` are unavailable (`tool-description.ts:105-107`). Saved `workflow()` children are loaded by host-side `scriptPath`/name resolution and execute as a one-level nested workflow sharing caps, journal/abort context and budget; a child workflow cannot itself nest (`tool-description.ts:88-89`; `runtime.ts:184-218`). A reusable skeleton must therefore inline/parameterize its graph through `args`, not import helper modules.
- `gate` is a shell command run after an agent and is bounded by 10 minutes (`src/workflow/host.ts:38-54`). For worktrees it must run in `onBeforeWorktreeCleanup`, before the worktree is deleted; running after spawn resolves would test the main tree (`host.ts:8-20`). Resume cannot combine with gate/schema/isolation/model/effort/agentType (`tool-description.ts:63-72,199-201`), so retries need a fresh gated verifier or explicit same-tree command.

## Worktree identity and merge contract

A worktree starts detached at the caller's current `HEAD`, records `baseSha`, and preserves the caller's repo-relative subdirectory (`src/worktree.ts:87-113`). This means if cwd is itself a worktree, base selection is that worktree's HEAD; there is no automatic discovery of the original/main worktree. A host adaptation must explicitly establish the intended integration root before dispatch if Go is invoked inside a worktree.

Cleanup commits changes, creates `pi-agent-<id>` (suffixing on collision), then removes the worktree (`src/worktree.ts:123-179`). Branch/base data is private manager/worktree metadata, not a script API field: `WorktreeInfo` records `baseSha`, and cleanup returns a branch only internally (`src/worktree.ts:23-29,87-113,156-174`). The public result's `cwd` is normally unset because cleanup removes the worktree before result construction (`src/workflow/host.ts:57-75,121-151`). If the leaf explicitly commits and leaves a clean worktree, cleanup creates the saved branch at that unchanged SHA (`worktree.ts:139-174`). If uncommitted changes remain, cleanup first creates an additional commit, whose SHA the already-finished leaf could not have reported. Viable pi-now contract: require each leaf to explicitly commit all intended work before its structured response, leave the tree clean, and return `git rev-parse HEAD`; require post-response gates not to modify product code or leave tracked output. A dedicated integrator verifies the returned commit object and ancestry/reachability before merging. Do not rely on future cleanup to commit and somehow report that future SHA. A predeclared named branch can be an additional convention only if the integrator/host can verify it; it is not exposed automatically. A future tiny extension envelope could add host-verified `{branch,baseSha,commit}` fields to `WorkflowSpawnResult`.

## Fixed Go lifecycle template

One workflow should own: setup → graph-ready dispatch → serial mechanical merge agent(s) → L2 (all intended inputs integrated **and** focused suite green) → L3 composition-root smoke where applicable → freeze → parallel standards/behavior review → at most two fresh fix rounds with delta review. Ready-set exhaustion is not completion; every planned slice must be integrated or explicitly blocked, including dependent consumers. Gate commands belong in repository files, not inline shell (`skills/rope-go/references/dynamic-workflow.md:56-95`). Pi's sandbox means merges should be delegated to a mechanical agent with the needed tools, or to a host adapter—not silently returned to the parent.

Use `agent(...,{schema})` for every machine-consumed result: `{status, slice, commit, evidence, setup}` (and optionally a predeclared branch name). Treat null, missing commit identity, failed setup, partial merge, and stale gate output as blocked. The child must report the SHA as data; the integrator verifies it against the repository rather than trusting prose. The mechanical merge executor must verify commit existence/ancestry/HEAD with Git commands and return their evidence. Schema validation checks shape, not truth; model-supplied commit data alone is not host verification. The workflow return is only a report; it is not proof unless all preconditions are mechanically asserted.

## Thin cross-harness comparison (official sources)

- **Claude Agent SDK:** its Python/TypeScript SDK exposes a query/session abstraction and streaming messages, with tool permissions and hooks; it is an SDK-native adapter, not a drop-in execution of pi's sandbox script. Official: https://platform.claude.com/docs/en/agent-sdk/overview and https://platform.claude.com/docs/en/agent-sdk/python.
- **Claude Code Dynamic Workflows (parent follow-up):** current official docs explicitly expose JavaScript `agent/pipeline/parallel`, literal `meta`, `args`, schema returns, no script fs/shell, similar agent caps, and prefix replay. The official blog recommends shipping JS in a skill as an adaptable template. This is a much closer counterpart than the SDK alone; exact pi agent options, preset names, worktree metadata and gate semantics remain untested across hosts. Official: https://code.claude.com/docs/en/workflows and https://claude.com/blog/a-harness-for-every-task-dynamic-workflows-in-claude-code . See `dynamic-go-template-and-parallelism.md` for verified scope/size guidance.
- **Codex:** official CLI/SDK surfaces are task/session oriented and sandbox/policy mediated; a pi JS script should be translated to a native adapter or degraded to explicit Agent dispatch, not presumed directly runnable. Official: https://developers.openai.com/codex/cli and https://developers.openai.com/codex/sdk.

Priority recommendation: optimize the pi-native template first. Cross-harness portability should mean the same graph/contract with verified host bindings (or the existing narrower fallback), not a premature universal runtime. Claude Code's native Dynamic Workflows make shared JS mechanics plausible, but compatibility requires a smoke probe; neither source similarity nor function names prove a drop-in execution.
